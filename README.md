# Edara — Officer Evaluation Committee System (نظام إدارة لجان تقييم الضباط)

A web rebuild of a legacy Oracle Forms system for managing officer‑evaluation committees.
The entire UI is **Arabic / right‑to‑left**, and all numbers are shown in **Arabic‑Indic digits**.

- **Client:** React 18 + Vite + TypeScript + Tailwind CSS
- **Server:** Node.js + Express + TypeScript (ESM), `sql.js` (SQLite compiled to WASM — no native build step)
- **Auth:** JWT, two roles: `admin` and `member`
- **Layout:** TypeScript monorepo — `client/` and `server/`

There are two committee types (`tagdded` = تجديد/ترقي and `edarya` = إدارية/قضائية) and three levels
(main / preliminary / commander). See `PROJECT_MAP.md` and `.cursor/rules/` for domain details.

## Prerequisites

- **Node.js 20+** (developed and tested on Node 24). npm comes with Node.
- No database server to install — `sql.js` runs in‑process and persists to `server/data/edara.db`.

## Install

From the repo root:

```bash
npm install
```

The root `postinstall` automatically installs the `server` and `client` dependencies too
(equivalent to `npm run install:all`), so a single `npm install` sets up all three.

## Two ways to run: Development vs Production

The app is built to run **two different ways**. Understanding the difference is the key thing:

| | Development (`npm run dev`) | Production (`npm run build` + `npm start`) |
|---|---|---|
| Processes | **Two:** API server + Vite dev server | **One:** the API server also serves the built UI |
| Ports | API `:3000`, UI `:5173` (open **:5173**) | Everything on `:3000` (open **:3000**) |
| Front‑end | Served by Vite (unbundled, Hot Module Reload) | Pre‑built static files (bundled + minified) |
| Server code | `tsx watch` (re‑runs TypeScript on change) | Compiled JS via `node dist/index.js` |
| `/api` calls | Vite proxies `/api` and `/api/ws` → `127.0.0.1:3000` | Same origin (no proxy needed) |
| Use it for | Local development | Deploying to a server / real users |

### Development

```bash
npm run dev
```

This runs (via `concurrently`):

- `dev:server` → `tsx watch src/index.ts` — the Express API on **http://localhost:3000**, auto‑reloading on file changes.
- `dev:client` → `vite` — the React dev server on **http://localhost:5173** with Hot Module Reload.

**Open http://localhost:5173.** The client's API base is the relative path `/api`, and Vite proxies
`/api` (and the `/api/ws` WebSocket) to the API server on `:3000` (`client/vite.config.ts`).

Verify types at any time:

```bash
npm run build            # or, per package:
( cd server && npx tsc --noEmit )
( cd client && npx tsc --noEmit )
```

### Production

In production there is **no separate front‑end server**. You build the client to static files,
and the Express server serves both the API **and** those static files on a single port. The client
talks to the API on the same origin, so no proxy or CORS juggling is needed.

1. **Build both packages:**

   ```bash
   npm run build
   ```

   - `server` → `tsc` compiles `server/src` → `server/dist`
   - `client` → `tsc -b && vite build` bundles `client/src` → `client/dist`

2. **Make the built client available to the server.** The server serves the folder in `CLIENT_DIR`
   (default: `./public`, resolved from the server's working directory). Either copy the build in, or
   point `CLIENT_DIR` at it:

   ```bash
   # Option A — copy the client build next to the server (simplest)
   cp -r client/dist server/public

   # Option B — point CLIENT_DIR at the existing build (absolute path)
   export CLIENT_DIR="$(pwd)/client/dist"
   ```

3. **Start the server:**

   ```bash
   npm start          # = node dist/index.js, run from the server/ directory
   ```

   **Open http://localhost:3000.** On startup you should see `Serving client from …` in the log,
   which confirms the UI is being served. Client‑side routes (deep links / refresh) fall back to
   `index.html`; anything under `/api/*` and the `/api/ws` WebSocket keep working normally.

> The static‑serving logic lives in `server/src/index.ts` and is **dev‑safe**: it only activates
> when a built client is present, so `npm run dev` is unaffected.

## Offline / air‑gapped deployment (self‑contained Windows bundle)

For a server with **no internet** (so `npm install` isn't possible on the target), the production
build is packaged into a single folder that runs with **zero prerequisites** — no Node install, no
`npm install`. This works because every *runtime* dependency is pure JavaScript/WASM (no native
modules), so nothing is OS‑specific except the bundled Node executable.

Bundle layout:

```
edara/
├─ node/node.exe          # bundled Node runtime (Windows x64)
├─ server/
│  ├─ dist/               # compiled server
│  ├─ node_modules/       # production dependencies only (pure JS/WASM, no .bin symlinks)
│  ├─ public/             # the built client (served by the server)
│  ├─ src/db/schema.sql   # needed on first boot
│  ├─ data/edara.db       # the database
│  ├─ package.json        # { "type": "module" } so `node dist/index.js` runs the ESM build
│  └─ .env                # PORT / HOST / JWT_SECRET
├─ start.bat              # cd server && ..\node\node.exe dist\index.js
└─ README-تشغيل.txt       # Arabic run guide
```

Run it: unzip anywhere → double‑click **`start.bat`** → open **http://localhost:3000** (or
`http://<server-ip>:3000` from other PCs on the LAN).

How it's produced (from a build machine **with** internet) — one command:

```bash
deploy/build-offline-bundle.sh              # Windows x64, fresh database (default)
deploy/build-offline-bundle.sh --with-db    # include the current server/data/edara.db
deploy/build-offline-bundle.sh --target linux-x64   # other targets
```

The script builds client + server, installs **production‑only** server deps, strips Unix `.bin`
symlinks, downloads/caches a Node runtime for the target OS/arch, and assembles + zips the whole
bundle (output: `deploy/dist/edara-offline-<target>.zip`). See `deploy/README.md` for details. Only
the script and templates are committed — the generated zip, the bundled `node` binary, and the
`.env` secret are not.

> Do **not** copy a Linux `node_modules` to Windows (or vice‑versa): npm's `.bin` launchers are
> per‑OS symlinks and some build tools ship per‑OS native binaries. Always regenerate `node_modules`
> for the target platform (which is exactly what the bundling steps above do).

## Configuration (environment variables)

Read from `server/.env` (loaded via `dotenv`) or the process environment:

| Variable | Default | Purpose |
|---|---|---|
| `PORT` | `3000` | Port the server listens on (e.g. set to `5173` if you prefer). |
| `HOST` | `0.0.0.0` | `0.0.0.0` = reachable on the LAN; `127.0.0.1` = this machine only. |
| `JWT_SECRET` | insecure fallback | Signing key for JWT sessions — **set a strong random value in production**. |
| `CLIENT_DIR` | `./public` | Folder of the built client to serve (relative to the server's working dir). |

## Data & database

- The database is a single SQLite file at **`server/data/edara.db`**, managed by `sql.js`.
- `sql.js` loads the whole file into memory and writes it back on save. **Stop the server before
  copying the `.db` file** to get a clean backup (and before overwriting it).
- Schema lives in `server/src/db/schema.sql`; additive migrations run on startup
  (`server/src/db/connection.ts`).
- Reference/lookup tables are seeded automatically; officer data is loaded via the quarterly SQL
  import screen (see `.cursor/rules/import-system.mdc`).

## Default login

- **Admin:** `admin` / `admin123` (change the password after first login).

## Scripts (root `package.json`)

| Script | What it does |
|---|---|
| `npm run dev` | Run server (`:3000`) + client dev server (`:5173`) together. |
| `npm run build` | Build server (`tsc`) and client (`vite build`). |
| `npm start` | Start the compiled server (`node dist/index.js`); serves the built client if present. |
| `npm run install:all` | Install `server` and `client` dependencies. |

Per‑package scripts also exist (e.g. `server`: `dev`, `build`, `start`, `seed`; `client`: `dev`,
`build`, `preview`).
